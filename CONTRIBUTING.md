# Contributing

Thanks for helping build better e-invoicing tooling for Australia and New Zealand. Contributions of every size are welcome — but some are more valuable than others, so read this first.

## The contribution we want most: fixtures

Real-world validation failures are gold. If your integration produced a document that failed PINT A-NZ validation in a way our corpus doesn't cover, a minimal reproducing fixture teaches every other integrator (and every tool in this repo) about that failure mode.

### Fixture rules

1. **One rule per file.** An invalid fixture must fail against exactly one business rule. If your document trips three rules, split it into three fixtures. (Schema-invalid XML is the one exception — see `fixtures/malformed/`.)
2. **Name it after the rule.** `invalid/ibr-cl-25.xml`, `invalid/aligned-ibrp-052-aunz.xml`. If a rule needs multiple variants, suffix them: `ibr-cl-25.wrong-scheme.xml`, `ibr-cl-25.missing-scheme.xml`.
3. **Strip everything real.** No real ABNs, NZBNs, business names, addresses, amounts, bank details, or invoice numbers. Use the shared test parties in `fixtures/parties.md` (checksum-valid dummy identifiers) so documents fail *only* for the reason they're named after.
4. **Declare the ruleset version.** Every fixture starts with a metadata comment:

   ```xml
   <!--
     fixture: ibr-cl-25.wrong-scheme
     expects: ERROR ibr-cl-25
     ruleset: <PINT A-NZ version, e.g. 1.x.x>
     notes: EndpointID uses scheme 0088 (GLN); A-NZ requires an approved scheme such as 0151 (ABN)
   -->
   ```

5. **Prove it.** CI runs every `valid/` fixture expecting zero errors and every `invalid/` fixture expecting exactly its declared rule to fire. `pnpm test:fixtures` runs the same check locally.

**Never commit a real invoice**, even partially redacted. If you're unsure whether something counts as identifying, don't include it — describe the failure in an issue instead and we'll help construct a synthetic reproduction.

## Other ways to contribute

- **Rule documentation** (`packages/rules`): plain-English explanations of what a rule means and how to fix a failure. Pair every explanation with a fixture.
- **Bug reports**: include the tool version, the ruleset version, the command you ran, and (synthetic) input that reproduces the problem.
- **Code**: see below.
- **Field reports**: even without code or fixtures, "here's what confused us when integrating" issues shape the roadmap.

## Development setup

```bash
# prerequisites: Node >= 20, pnpm >= 9
git clone <repo-url>
cd <repo>
pnpm install
pnpm build        # builds all packages
pnpm test         # runs all tests, including fixture verification
```

This is a pnpm workspaces monorepo. Each tool lives in `packages/<name>` and is developed, tested, and published independently. Run a single package's tests with `pnpm --filter @pint-anz/lint test`.

## Pull request conventions

- **Small PRs merge fast.** One fixture, one rule doc, one fix per PR.
- **Conventional commits** (`feat:`, `fix:`, `docs:`, `fixtures:`) — they drive the changelog.
- New CLI behaviour needs a test; new output formats need a snapshot test.
- If a change alters validation results (e.g., a ruleset upgrade), call it out prominently in the PR description — downstream CI builds depend on stability.

## Ruleset versioning policy

PINT A-NZ is a living specification. This repo pins one ruleset version per release of each tool; upgrading the ruleset is always a **minor version bump at minimum** and always noted in the changelog, so a spec release never silently changes your build's results. Issues reporting drift between our bundled ruleset and the latest official release are always welcome.

## Conduct

Be kind, assume good faith, and remember most people here are wrestling with Schematron for the first time. Harassment of any kind isn't tolerated. Disagreements about rules are settled by fixtures, not volume.
